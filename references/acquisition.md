# 获取源码与准备二开

## 进入条件

已有具体仓库选择，且任务包含获取源码；或已明确委托自动选型并下载。沿用上下文授权，不重复问。仅“找几个类似项目”到比较报告为止。

拟把源码作为开发基底时，先核实许可与用途。不确定时补证据或选择其他实现；不擅自去除原许可证、版权说明或改成自己的许可证。用户提供已有授权时纳入判断。

## 获取方式

| 方式 | 适用情况 | 成功条件 |
| --- | --- | --- |
| 本地 Git 克隆 | 保留历史、跟踪上游 | URL 正确、commit 一致、所需工作树文件存在 |
| 固定 commit 源码归档 | 只需快照或没有 Git | 来自所选仓库的固定 commit，完整解包并记录摘要 |
| 逐文件读取 | 只需少量模块或整库获取受限 | 列已取文件和缺失项，状态明确为 partial |

本地 clone/fetch 可使用 Git；这不授权 push、远程建仓库或远程 fork。GitHub 远程写操作只通过已连接的 GitHub 插件，除非用户明确改变偏好。插件没有整库下载工具时不伪造该能力。

## 固定版本与目录

1. 接受用户指定的 tag/branch/commit；未指定则按功能选择合理版本，说明稳定发布或默认分支的选择原因。
2. 将 ref 解析并核验为完整 commit SHA，记录所选 ref 和实际 SHA；不能用最近提交搜索结果替代分支 HEAD。
3. 在同一 commit 下复核拟复用路径和许可，先前默认分支的发现证据仅作线索。
4. 服从用户指定目录；否则选工作区新目录。解析绝对路径，检查已有内容，不覆盖或删除现有工作，重试也不清空未知目录。
5. 只使用核实的仓库 URL，不从 README 复制任意下载命令；参数与代码分离，不把 repo 名和路径拼成可执行 shell 文本。

## 完整性与执行边界

- 克隆后核对 remote URL、HEAD SHA、初始工作区状态；浅克隆不是完整历史。
- 归档使用固定 commit 地址，核对来源、解包路径与关键文件。记录 SHA-256 供追溯，不把本地计算摘要称为独立真实性证明。
- 解包前检查绝对路径、路径穿越和会逃出目录的链接；使用新目录，不自动覆盖已有文件。
- 检查 `.gitmodules`、Git LFS 指针和生成文件依赖；未取得的必要子模块、LFS 对象等列为缺失。先核实外部资源来源与必要性，不自动递归执行。
- 获取源码不运行安装、构建、启动、postinstall 或远程脚本。用户已要求实施时，可在检查相关脚本、依赖和环境后执行必要安装与验证，不增加例行确认。
- 下载失败留下文件时，核对它是否属于本次获取，再续传或选新目录；记录原因，不重复整套选型。

## 交接

按 [outputs.md](outputs.md) 在报告目录写 `source-record.json` 和 `development-plan.md`，不混入第三方源码。

二开计划先写上游功能与需求对应，再写最小改动范围、扩展点和验收方式。保留许可、版本与来源；是否建远程仓库、发布、贡献上游由用户任务决定。

仅完成下载时写“源码已获取，尚未运行”。用户要求实施时先记录上游基线，再修改验证；不把上游原有失败归因于自己的改动，不把下载成功当作功能完成。

## 已实现命令

具体参数见 [cli.md](cli.md)。scripts/reuse.py acquire 接收 inspection.json、review.json、全新源码目录与独立的全新报告目录。默认固定 commit 归档，也支持浅 Git 获取；逐文件比较 Git blob，许可文件再核对 SHA-256。Git 配置与钩子不会被下载流程执行。

file_subset 是手工逐文件获取时的记录类型，acquire 命令只实现 archive/git 两种整库获取路径。validate 命令验证记录的不变量，不复验二开后被修改的源码。脚本生成的交接初稿需补全真实需求与模块分析。
